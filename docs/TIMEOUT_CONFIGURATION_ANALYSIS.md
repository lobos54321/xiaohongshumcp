### 场景：页面超时 < MCP 超时

```

MCP 超时：600秒
实际需要：312秒

结果：

│ 0秒    开始发布                              │
│ ...    正常进行                              │
│ 300秒  Rod 超时 panic！❌                    │
│        MCP 接收到 panic 错误                 │

└──────────────────────────────────────────────┘

问题：
✅ 如果元素找不到，会快速失败（好处）
❌ 但实际发布需要 312 秒，300 秒不够！（致命）
❌ 正常发布会在 300 秒时失败
```


## ✅ 为什么 600 秒是合理的

### 场景：页面超时 = MCP 超时

```
页面超时：600秒
MCP 超时：600秒
实际需要：312秒

正常情况：
┌──────────────────────────────────────────────┐
│ 0秒     开始发布                             │
│ ...     正常进行                             │
│ 312秒   发布完成 ✅                          │
│         MCP 返回成功（在 600 秒内）          │
└──────────────────────────────────────────────┘

异常情况（元素找不到）：
┌──────────────────────────────────────────────┐
│ 0秒     MustElement 开始查找                 │
│ ...     找不到元素，一直等待                 │
│ 600秒   Rod 和 MCP 几乎同时超时              │
│         可能有竞态，但结果一致：超时错误     │

优点：
✅ 足够完成正常发布（312秒 < 600秒）
✅ 有 288 秒缓冲（接近 5 分钟）
✅ 不浪费时间（异常时 600 秒即失败）
✅ 时间一致，行为可预测

缺点：
⚠️ 可能有轻微竞态（两个超时同时触发）
```

## 🔑 关键洞察

### 问题的本质不是超时配置

```
真正的问题：
❌ MustElement 会等待整个页面超时
❌ 找不到元素时，不管超时是多少，都会等待那么久

正确的解决方案：
✅ 不使用 MustElement
✅ 使用 Element + 独立的短超时重试逻辑
✅ 元素查找：30 秒独立超时
✅ 页面超时：600-900 秒（足够完成发布）
```

### 超时的真正作用

```
元素查找超时（30秒）：
作用：快速发现元素不存在
实现：自定义重试逻辑

页面操作超时（600-900秒）：
作用：防止整个页面卡死
包含：所有 Rod 操作的总时间

MCP 服务超时（600-1200秒）：
作用：最外层保护，防止服务卡死
应该：> 页面操作超时
```

```
⚠️ 异常时浪费 300 秒
```
